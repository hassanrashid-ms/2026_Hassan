The tenancy boundary

Exactly two tables have no workspace_id: workspace and agent. Every other table carries one and gets the identical RLS policy, applied structurally in 002_rls.sql — any base table with a workspace_id column, not a hand-maintained list — so a new table can never ship without its policy.

Global — no tenancy

  • workspace
  • agent

One Google login per person, global across workspaces. Their role is not.

The hinge

  • workspace_member

Carries the per-workspace role. An agent on three games has three rows.

Scoped — RLS on the remaining 25

  • every other table

USING (workspace_id = current_setting('app.workspace_id', true)::uuid), FORCEd so it binds the table owner too.

article_version is the one exception — it has no workspace_id column at all (it draws its parent from article_id alone), so it gets a hand-written policy instead of the generic one: article_id IN (SELECT id FROM article WHERE workspace_id = current_setting(...)). Structural discovery of "scoped" by column presence misses it on purpose, and 002_rls.sql adds it explicitly right after the loop.

How writes are constrained beyond RLS

Mechanism Where it's used
REVOKE UPDATE, DELETE event, change_log, bot_config_version, form_answer — each an append-only log. Revoked from support_app and crm_admin (which otherwise has BYPASSRLS), so no application role can rewrite history.
Per-row trigger article_version: a BEFORE UPDATE OR DELETE trigger raises once status = 'published'. A blanket REVOKE doesn't work here because the same table also holds the mutable draft row — the trigger enforces "published rows never change" per-row instead of per-table.
Composite FK on (workspace_id, id) Applied where a client-supplied id could otherwise cross a tenant boundary through a parent chain the database can't see through RLS alone (FK checks run with row security suspended) — conversation → subintent, resolution_cycle/form_submission → conversation, form_version/form_submission → form, form_answer → form_submission, conversation_tag → conversation, tag, subintent → form. See docs/decisions/2026-08-04-composite-foreign-keys-for-tenancy.md. Simpler parent references (session → player, conversation → player, message → conversation, event → conversation/session) stay single-column and rely on the handler having already proven the id visible with a scoped SELECT — CLAUDE.md's rule that FK checks bypass RLS.
No DELETE grant, anywhere support_app and crm_admin both get SELECT, INSERT, UPDATE only. "No hard deletes" is a grant that doesn't exist, not a convention every route has to remember.
Column-scoped GRANT workspace itself is otherwise read-only to support_app (writing secret_hash would let a bug lock out another tenant's players); ticket_seq, max_assigned_tickets, auto_close_days, inactivity_window_hours and form_timeout_minutes are granted back column-by-column for the request paths that legitimately bump or tune them.

agent holds a Google identity, not a credential — there are no passwords in the product, and google_subject is only null for a seeded row awaiting its first real login. workspace.secret_hash from the original design was replaced by workspace_secret as its own table: rotation inserts a row rather than overwriting one, so the previous secret keeps working through a grace window while a game studio redeploys. session.id is the one primary key the server does not generate — the SDK mints it before any network call, so POST /sdk/sessions/start is idempotent via ON CONFLICT (id) DO NOTHING, not a dedupe table.

Promotion is not retroactive. declared_field is the admin-managed key set; the split between player_state_snapshot.declared and .raw is decided at write time, against whatever was promoted then. Promote a key today and every earlier snapshot keeps it in raw — there is no backfill, ever.

There is no rules engine or label table here — the original design's RULE, RULE_FIRING and LABEL/CONVERSATION_LABEL never shipped. tag/conversation_tag is what exists instead: flat, admin-created tags with soft removal, applied and removed directly rather than auto-derived from a subintent mapping. article_version doubles as both the draft store and the append-only version history — exactly one draft row per article (partial unique index), one published row per publish, and discarded for an abandoned draft that is never deleted.

Retrieval is Weaviate, not a column here. The original design put embeddings in pgvector/HNSW as their own table. Bot retrieval is now BM25 search over Weaviate Cloud (see docs/specs/2026-08-07-weaviate-faq-search-design.md), external to Postgres — there is no article_embedding or article_phrasing table to keep in sync with it.

Table definitions for the diagram above — the exact mermaid/schema source.

message.seq is server-assigned, never a device clock — order matters, gaps don't, and internal notes still consume sequence numbers so the player's view legitimately has holes. visibility is never filtered in a query; two serializers (toAgentView, toPlayerView) do that, so anything unexpected fails closed rather than leaking a note. resolution_cycle is a mutable projection, not an append-only log — unlike event/change_log/form_answer, it has no REVOKE UPDATE, because inactivity_due_at ticks forward for the life of the cycle. A partial unique index (WHERE resolved_at IS NULL) makes "at most one open cycle per conversation" a database guarantee rather than a reopen-handler responsibility.

Attachment claim is a state, not a lifecycle column. No attachment row exists until the owning message actually sends — an abandoned upload is bytes in object storage under a per-player prefix, never a database row. There is deliberately no status column and no reaper job for this table.

Fields live as a jsonb array on form_version, not a separate form_field table — editing a live form mints a new version and its fields move with it. form_answer is REVOKE UPDATE/DELETE: a correction is a new row for the same field_key, newest created_at wins, both stay traceable. Seven field types are declared in form_field_type but only six are usable — time is declared and must not be offered by the form-builder, and attachment is declared-but-inert until it's wired to a delivery path.

Table definitions for the diagram above — the exact mermaid/schema source.

bot_config is the one table keyed directly by workspace_id as its primary key — there is exactly one row per workspace, seeded the moment a workspace is provisioned, and its only writer is INSERT ... ON CONFLICT (workspace_id) DO UPDATE (which is why it keeps UPDATE where the other three logs on this page don't). bot_config_version and change_log both audit it, at different grains: bot_config_version is a full four-field snapshot per save (so "what did the whole bot look like at v3" is one row), while change_log is generic and field-level, with a CHECK that rejects a no-op change. There is no RULE/ RULE_FIRING engine — the bot's conditional behaviour resolves from rules/tools_config/limits_config at request time in domain/bot/*, not from a separate rules table.
