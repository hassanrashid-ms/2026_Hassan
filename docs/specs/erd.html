PostgreSQL, and the 32 tables that follow from it

The stack doc picked Mongo before the deployment target was known. Self-hosting settles it, and nothing is built yet. Seven schema decisions worked through, five unspecified behaviours pinned down, every table accounted for, and the SDK wire contract reconciled against it.

PostgreSQL 17 Drizzle ORM pgvector · HNSW Row-Level Security Redis + BullMQ 32 tables

Why the decision flips

Four requirements carry real weight. Three favour Postgres on merit; the fourth is settled outright by self-hosting.

RequirementOn MongoDBOn PostgreSQL
Bot retrieval
Vector search over published articles		 Not available. Atlas Vector Search runs as a separate mongot process that exists only on Atlas — it is not in Community Edition. Self-hosting leaves in-process cosine, which every API replica holds its own copy of, so a manual re-sync only fixes the instance that served the request. pgvector in the same container. One image, one backup, one transaction.
Tenant isolation
"The highest-risk thing in the build"		 A Mongoose global plugin with pre hooks. Bypassed by .aggregate(), by paths that skip middleware, and by any raw driver call. The stack doc already flags aggregate as "the one people forget." RLS policies enforced by the engine. A query with no workspace_id predicate returns zero rows — no code path around it, including raw SQL and psql.
Event-sourced reporting
9 metrics, date range + comparison period		 Aggregation pipelines. "Resolutions per active agent-day, split player-confirmed vs timed out, vs the prior period" is several hundred lines of $facet nobody wants to modify in week 3. GROUP BY with FILTER, window functions for sparklines, generate_series to gap-fill empty days.
"Nothing is deleted"
No hard deletes anywhere		 A code convention, enforced by everyone remembering. Foreign keys with ON DELETE RESTRICT. The database refuses.

The one thing Mongo genuinely wins is the freeform state.raw blob the SDK sends — arbitrary keys, no schema, never dropped. JSONB with a GIN index covers that completely, and the declared-field wildcard index the stack doc describes maps onto a GIN index one-for-one.

Cost of switching: zero. frontend/ and backend/ contain nothing but a README. No schema to migrate, no data to move, no code to rewrite — three documents to correct. This is the last moment the switch is free.

Drizzle, not Mongoose or Prisma

The stack doc chose Mongoose "specifically for the plugin/hook system the tenancy guard needs." Under RLS that requirement disappears — the guard moves into the database, so the ORM stops being the security boundary. Three things then decide it:

  • RLS needs session variables. Every request runs SET LOCAL app.workspace_id inside its transaction. Drizzle's transaction API makes that a one-line wrapper; Prisma needs $executeRaw threaded through interactive transactions and loses the guarantee whenever someone forgets.
  • Reporting is SQL-shaped. Drizzle's sql template keeps window functions and FILTER clauses typed and inline. Prisma pushes them to $queryRaw, outside the type system.
  • pgvector is a first-class column type in Drizzle. Prisma models it as Unsupported(), which cannot be selected through the client.

The tenancy boundary

The schema's organising idea. Exactly two tables have no workspace_id. Everything else carries one and gets the identical RLS policy.

Global — no tenancy

  • workspace
  • agent

One login per person. An agent row is global; their role is not.

The hinge

  • workspace_member

Carries the per-workspace role. An agent on three games has three rows and may hold a different role in each.

Scoped — RLS on all 29

  • every other table

One policy, repeated: workspace_id = current_setting('app.workspace_id')::uuid

Write the isolation test on day one. Authenticate as workspace A, then hit every endpoint with workspace B's IDs. Under RLS the expected result is 404, not 403 — the rows are invisible, so the handler genuinely cannot distinguish "not yours" from "not there." That is correct, and it should be asserted rather than discovered.

SESSION exists purely as the denominator for self-serve rate — counted per session, never per ticket. Three load-bearing choices. Articles hang off intent, never subintent — one article usually answers several subintents at once, so attaching it lower would mean duplicating it or the bot missing it. Embeddings are their own table, one row per summary and per phrasing, so retrieval matches the phrasing that hit and returns the body — body text full of "tap the button below" retrieves badly. ARTICLE_FEEDBACK is not optional: two reporting panels cannot exist without the "did this help / did this solve it" signal, so it is captured from the first article a player ever reads.

Both levels are Admin-editable, and TAXONOMY_CHANGE logs edits to either. The spec's p44 matrix grants Admin "create or rename a subintent" and "archive, move or merge a subintent" — and has no intent row at all, despite discussing intents throughout. That reads as an omission rather than a prohibition, since "changing taxonomy must never require a release" covers intents too. So entity_type plus a nullable intent_id/subintent_id pair with a CHECK that exactly one is set.

kind includes create, which rev 2 missed. p14 says rising volume in Other is a direct instruction to add a subintent — so when support acts on it, Other's volume drops. That drop is someone reorganising the list, not player behaviour changing, and it needs a date exactly like a merge does.

Archiving an intent is blocked-if-not-empty — unlike a subintent. Refuse while it still has non-archived subintents, because cascading would silently archive several categories in one click; each child should be a deliberate, dated act. Refuse while it still has published articles, because articles hang off intents and the bot would be left holding content in a category that no longer exists. Other is refused always, via is_system. Write this asymmetry down or someone implements a cascade.

And because Other is an intent while conversations store a subintent, the first migration seeds a catch-all subintent beneath it. That also keeps two distinct states apart: the Other catch-all means the bot ran and decided the issue fits nothing, whereas subintent_id IS NULL means the bot never ran — errored, timed out or disabled — which is its own metric. Folded together, a broken bot looks like a taxonomy gap.

Five deliberate choices. Messages are their own table, ordered by a server-assigned seq from an atomic increment on the conversation row — never device clocks; gaps are fine, order is not, and internal notes consume sequence numbers so the player's view legitimately has holes in it. Only the subintent is stored; the parent intent is derived through the join, so an edited taxonomy can never leave the two drifting apart. visibility lives on the message and is never filtered in the query — the player serializer whitelists fields and returns null for anything not public, so anything unexpected fails closed. Resolution state left conversation entirely, which is what makes per-cycle reporting possible. And ATTACHMENT has exactly one parent — a message — because forms are conversational, so an attachment answer arrives as an ordinary image message.

Signing a presigned GET must check the parent message's visibility. If an agent attaches a screenshot to an internal note, the message is hidden by the player serializer but the file still sits behind a signable key. The signing endpoint has to walk attachment.message_id → message.visibility and refuse for a player token when it is not public. This is the one that gets missed, because the thread renders perfectly while the attachment leaks.

Editing a live form mints a new FORM_VERSION; fields belong to the version, not the form. Because every submission is stamped with the version it used and answers point at that version's fields, answers collected last month still read correctly after the questions change. A skipped or partial form is a row, not a missing row — the agent has to see that the player declined rather than wondering where the details went. A merge never disturbs submitted answers either: they reference a form version, not a subintent.

The form is a conversation, not a modal. The bot asks the questions as messages in the same thread and the player answers as ordinary messages. The spec supports this directly — Forms is one of the four bot settings tabs (p26–27), and p28 says "structured questions… shown by the bot at step 6." Only the builder side is ever wireframed. p28's "skippable — an option at the bottom of every form" becomes: the skip is offered alongside every question, which is satisfied more strongly than in a modal since "Talk to a person" is on every screen anyway.

That shapes three columns. status replaces a was_skipped boolean, because in a conversation the player can answer two of five questions and go silent — partial is reachable in a way it never was with an atomic submit, and those answers must not be lost. The row is therefore created when the bot asks the first question, hence started_at and a nullable submitted_at. message_id on each answer keeps the player's actual words reachable, because the bot is extracting structure from prose — "iOS 26.5, and I'm on 6.2 I think" is one message answering two fields, with hedging. And corrections add rather than update: a second row for the same field, newest by created_at winning, both traceable.

Two things deliberately have no column. The bot's position in the questionnaire is derivable — lowest position with no answer — so there is no cursor. And is_required is soft: the bot asks, and if the player says "I don't know" it re-asks once, then moves on and records the field unanswered. A bot that blocks on a required field would break the hard constraint that nothing may prevent a player reaching a human.

Uploads: an unsent file is deleted

Because no attachment row exists until a message sends, an abandoned upload is only bytes in a bucket. Three triggers remove them, and all three are needed — the first two cover the paths where the client tells you what happened, and the third covers the one where it never does.

TriggerWhenWhat happens
Player cancels Removes the file from the composer, or closes the composer with a staged file DELETE /uploads/{key} — the object is deleted immediately. Authorised by putting the player id in the key path, so no database row is needed to prove ownership.
Message sends The good path CopyObject to attachments/, then delete the pending/ original. Nothing lingers and you never pay to store the file twice.
Client never returns Force-quit, crash, lost connectivity, player walks away A bucket lifecycle rule expires everything under pending/ after 24 h. Mandatory — no cancel request is ever coming, so without this the bytes are permanent. 
-- ownership is encoded in the key, so no DB row is needed
ws/{workspace_id}/pending/{player_id}/{uuid}     -- unclaimed, expires in 24h
ws/{workspace_id}/attachments/{uuid}             -- claimed, permanent

-- DELETE /uploads/:key  authorises by comparing the token's
-- player_id to the segment in the path. A player cannot reach
-- another player's pending upload, or anything under attachments/.
This does not conflict with "nothing is deleted." That rule protects records — messages, conversations, subintents. An unsent upload has no attachment row, appears in no thread, and no agent ever saw it. It is not a record; it is uncollected garbage. The moment an attachment row exists, the object becomes permanent like everything else, and there is no route that removes it.

One portability note. The pending/ prefix plus a copy on claim works identically on S3 and R2. The alternative — upload straight to the final key and tag it state=pending, expiring by tag so large videos are never copied — is cheaper for video but relies on tag-based lifecycle filtering, which R2 does not match S3 on. Since the stack doc still says "S3 or Cloudflare R2", the prefix approach keeps that choice open.

Merge, in full

The operation that got the most attention, so worth writing out. Admin only, per the p44 matrix. One transaction, five writes.

BEGIN;

-- Lock both rows so two concurrent merges cannot interleave
SELECT id, archived_at, merged_into_id, intent_id, is_system
  FROM subintent
 WHERE id IN (:survivor, :loser)
   FOR UPDATE;

-- 1 · reassign the conversations, and record what happened to each one
WITH moved AS (
  UPDATE conversation
     SET subintent_id = :survivor
   WHERE subintent_id = :loser
  RETURNING id
)
INSERT INTO event
  (workspace_id, type, conversation_id, actor_id, actor_type, occurred_at, payload)
SELECT :ws, 'subintent_merged', moved.id, :actor, 'agent', now(),
       jsonb_build_object(
         'from_subintent_id',   :loser,
         'from_subintent_name', :loser_name,      -- snapshotted
         'to_subintent_id',     :survivor,
         'to_subintent_name',   :survivor_name,
         'taxonomy_change_id',  :change_id)
FROM moved;

-- 2 · archive the loser, leaving a forwarding address
UPDATE subintent
   SET archived_at = now(), merged_into_id = :survivor
 WHERE id = :loser;

-- 3 · compress the chain so lookups stay depth-1
UPDATE subintent
   SET merged_into_id = :survivor
 WHERE merged_into_id = :loser;

-- 4 · record the structural change and its date
INSERT INTO taxonomy_change (workspace_id, entity_type, subintent_id, kind,
       survivor_subintent_id, from_intent_id, to_intent_id,
       before_name, after_name, conversations_moved, actor_id, occurred_at)
VALUES (:ws, 'subintent', :loser, 'merge', :survivor, :a, :b,
        :loser_name, :survivor_name, :moved_count, :actor, now());

COMMIT;

-- then, AFTER commit: enqueue the bot knowledge sync.
-- An archived subintent the bot still knows about keeps being used.

Why the per-conversation event matters. Without it, a ticket's history reads as a contradiction — classified as one thing, currently another, nothing in between. With it, the ticket explains itself:

14 Mar 09:12Player: "paid but no gems" 14 Mar 09:12Bot offered "Purchase didn't arrive" 14 Mar 09:14Player said it didn't help 14 Mar 09:15Classified as "Double charge" by bot 3 Apr 11:40Moved to "Payment failed" — taxonomy merge by Sara (admin) nowSubintent: Payment failed

Names are snapshotted into the payload because the survivor can be renamed later, and the loser is archived but still renameable. Without snapshots, a March entry silently rewrites itself to use today's labels. Same principle as the article title on a bot offer: a record of what happened, not a pointer to live content.

Separate event types also protect a metric. Misclassification rate counts conversations where an agent changed the subintent. If a merge were indistinguishable from a reclassification, one admin tidying the list would spike every agent's apparent error rate. intent_corrected and subintent_merged stay distinct.

The bug merge creates: saved filters. A saved_filter.definition can contain subintent_id = <loser>. After a merge that filter silently returns zero rows forever, and it reads as a bug rather than a merge. Fix it both ways — resolve merged_into_id on read so stale links and bookmarked URLs degrade gracefully, and rewrite stored filter definitions in the same transaction so they stay honest rather than permanently indirect.

Generalise it: any bulk operation that touches conversations emits a per-conversation event, not just a summary row. The summary tells you the list changed; only the per-ticket event tells you what happened to a ticket. Merge is the first case. Deactivating an agent — which returns all their open conversations to the unassigned queue — is the second one you will hit.

FeatureWhat it buys

The five unspecified things, now decided

QuestionDecision
Cross-intent merge Allowed. Blocking it would only force an admin to do two operations to achieve the same thing. Both from_intent_id and to_intent_id land on the taxonomy_change row, so the intent-level volume shift is as explainable as the subintent-level one.
Snapshot on reopen Keeps the original — and this is now structural. The snapshot is keyed to session_id, not conversation_id, because the SDK delivers it on POST /sdk/sessions/start before any conversation exists. A conversation reaches it via conversation.session_id, and a reopen happens in a new session without ever rewriting that FK — so the original is what the Game View shows, enforced by the graph rather than by a rule. Consequence: a player reopening six months later sees a six-month-old device and client version, so captured_at must be displayed prominently or an agent will hunt a bug in a build that no longer exists.
Auto-close window 7 days, per-workspace setting. Lives in the admin console, per "anything that would otherwise need a release to change belongs here instead."
Events: projection or truth Projection. CONVERSATION stays a mutable row the console reads directly, and every state change also appends to EVENT. The cost: a bug can let the row and the stream disagree, so all state changes go through one function that writes both in a single transaction — never ad-hoc updates.
Who creates an intent An Admin, in the dashboard. The p44 matrix enumerates subintent operations and has no intent row at all, despite the spec discussing intents throughout — an omission rather than a prohibition, since "changing taxonomy must never require a release" covers intents. Same permission level as subintents. Three consequences: taxonomy_change gains entity_type, kind gains create, and archiving an intent is blocked-if-not-empty.
Auto-close is the lowest-value worker in the build — schedule it last. Push on what closed achieves and most of it evaporates: the player sees "Resolved" either way, reopening works identically from both with no time limit, and the inactivity clock has already stopped. It does not even serve reporting, because the counting rule is "resolution counts events, not current status" — so reports aggregate conversation_resolved events, which the event table does better than a status field. What genuinely remains is queue hygiene: the line between "resolved an hour ago, might bounce back" and "resolved last month, file it." Worth building, worth building in week 3.

Why 32 tables

It sounds like a lot until you notice where they come from. Twelve tables are things the product has. The other twenty are the price of three rules you wrote yourself.

Rule 1 · Nothing is deleted

  • taxonomy_change
  • event
  • rule_firing
  • change_log
  • resolution_cycle

Corrections are made by adding, so every correction needs somewhere to be added. A product that allowed deletes would drop all five.

Rule 2 · Support configures without a release

  • intent
  • subintent
  • form
  • form_version
  • form_field
  • label
  • rule
  • bot_config
  • declared_field
  • saved_filter

Every one of these would be a constant in the codebase if a release were acceptable. They are tables because it isn't.

Rule 3 · Reporting counts events

  • session
  • article_feedback
  • article_embedding
  • article_phrasing
  • player_state_snapshot

Metrics that cannot be derived from current state need their raw material captured at the time it happens.

Where I'd accept fewer

Four of the 32 are genuinely collapsible. I'd take one of them and keep the rest, and here's the honest reasoning on each:

CandidateVerdict
form_field Collapsible; kept. Fields are only ever read as a whole set, so they could be jsonb on form_version. Kept as a table because form_answer FKs to it, and because the bot walks fields by position to decide what to ask next.
bot_config Keep. It looks like columns on workspace, but workspace is one of only two global tables and this is workspace-scoped config under RLS. Merging it would put tenant-scoped data in an untenanted table — exactly the confusion the tenancy boundary exists to prevent.
player_state_snapshot Keep — and it can no longer be collapsed at all. It is 1:1 with session, not conversation, and a session may never produce a conversation, so there is nothing to fold it into. Independently: raw is uncontrolled client input treated as PII by default with its own retention rules, and it's a potentially large blob you never want dragged through a queue list query.
change_log Keep. It could fold into event as one append-only log. But event is scanned constantly for metrics across millions of rows, and mixing rare config audits into it means every metric query wades through noise. Different write rate, different read pattern, different index strategy.

Every table is kept, so the count stays 32. Going lower means dropping a spec requirement rather than normalising differently — and the cheapest-looking cuts are the most expensive: session, article_feedback and event are three small tables whose data cannot be reconstructed later. Skip them in week 1 to save time and weeks 1–2 have no metrics at all.

The SDK seam — what reconciling it changed

The SDK's production spec froze a 4-endpoint wire contract before this schema existed, with the rule "add response fields freely; never remove or retype one — old builds sit in app stores for years and cannot be recalled." Checking one against the other found five mismatches. All are now fixed; the full server side is in docs/specs/2026-08-04-sdk-wire-contract.md.

What the SDK sendsSchema beforeFix
sessions/start carries the snapshot player_state_snapshot.conversation_id was UK NOT NULL — and no conversation exists at session start, because the web app only creates one when the player sends a message Re-keyed to session_id. Also makes late arrival harmless and makes "a reopen keeps the original snapshot" structural
entry_point no column session.entry_point text — free text, not an enum, so a game can add one with no server release
A client-generated sessionId session.id was server-generated Accept the client UUID as PK → ON CONFLICT DO NOTHING gives Outbox idempotency free
sessions/end carries articles read no article_read event — only article_feedback, which is the separate "did this help?" signal Added article_read and still_need_help_reached. p40's four-step funnel needs both
POST /sdk/incidents no home at all An event row, type = 'sdk_incident'. Low volume, and it inherits workspace scoping, BRIN and append-only
Two failure modes worth naming. A snapshot that arrives malformed, empty or not at all must still return 200 and write a row with is_missing or degraded_reason — rejecting it would mean the conversations where something is broken are precisely the ones that fail to attach context. And a sessions/end that never arrives must not shrink the self-serve denominator: count sessions by started_at, never ended_at, and timeout-close stragglers after 30 minutes. Otherwise self-serve rate rises exactly when the SDK is misbehaving.

Build order is sequential, solo: schema + RLS → the five endpoints → a deliberately ugly web stub that reads #t= and calls close → the real SDK → and only then conversations, messages and the chat UI. The seam spans both repos and is where the surprises live, so it gets proven while it is still cheap to change.
